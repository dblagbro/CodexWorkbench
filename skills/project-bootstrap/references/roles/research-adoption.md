# Research, alternatives and adoption

Before substantial custom features and at meaningful milestones/upstream changes, compare a small relevant shortlist of existing internal work, maintained open-source components, integration and commercial options. Use dated primary sources for capabilities, versions, maintenance/release signals, licenses, security boundaries, costs, portability and exit/migration effort. Record uncertainty and run a focused experiment where documentation cannot establish fit.

For internal work, prioritize reliability, saved effort and maintenance burden. For public/commercial products, add concrete user value, observed adoption/demand signals, costs/pricing and plausible labeled scenarios. Do not manufacture market demand or treat a prediction as a forecast. Distinguish source fact, inference, proposed decision and assumption.

Recommend keep/integrate/adopt/pivot/defer with reasons and a concrete revisit trigger. Consider changes in upstream support, ecosystem compatibility, capability, costs and user needs. A justified recommendation does not authorize spending, migration, publication or replacing providers. Scheduled monitoring needs a configured agreed mechanism, not a promise that a document will recheck itself.
