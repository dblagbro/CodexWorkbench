# Prepare capabilities without growing context unnecessarily

When a design feature enters scope, identify the concrete capabilities it needs: relevant installed skills, native CLI/API, project adapters, browser access, and any distinct specialist role. Inspect existing tools before adding dependencies. Load the applicable skill instructions once at that point, including mandatory prerequisites; do not preload unrelated skill bodies, tool schemas or agents. Configure/install only dependencies actually needed and authorized by the feature. Being listed, installed, authenticated, usable and verified are different states.

Retain a compact project capability/context record using existing project notes when useful: feature, tool/skill path and revision/hash, relevant summary, owner host, verification date, evidence pointer, unresolved needs. Track material source changes through Git diffs/hashes rather than repeatedly rereading full manuals or chat history. Reuse what is still in current context; reread changed sections, missing details after compaction, or freshness-critical facts. A "read once" record is not proof that all instructions survived context loss. Required instructions and current host/security/production state still need relevant verification. Do not create a document for every tiny task.

Use concise status/decision records as the durable source of project memory. Prefer targeted file ranges, ripgrep, structured jq/Python queries, native session metadata and a narrow KB query over whole logs/transcripts. Batch independent tool reads where useful, cap output deliberately, and preserve full raw evidence in private files only when needed. Never cache secrets or raw private prompts to save tokens.

Use native provider memory only when supported/configured, with attention to privacy and freshness. It complements explicit instructions and verified project records; it is not guaranteed shared cloud memory, cross-host memory or a substitute for checking sensitive live state. Do not enable experimental memory flags, change model quality, disable checks or weaken permissions just to reduce context. Do not promise cache hits or token savings without measurements.

For substantial work, use authorized specialists when there is a distinct parallel task or independent review. Give a focused task, ownership, required references and acceptance criteria; request a concise evidence/results handoff. Reuse relevant agent findings in the same session when still valid. Do not spawn idle agents or copy the entire conversation into every agent merely to keep them "warm". Agents consume tokens and can add latency; persistent identities/caches are provider-specific, not an assumption.

Favor existing maintained CLI/API tooling, metadata adapters and deterministic scripts before another MCP server or model call. Popularity alone does not establish safety or a performance benefit. Before adding an optional third-party helper, check source/license, maintenance, dependency/security exposure, data sent outside the environment and measured usefulness on a representative task. Compare elapsed time, total input/output tokens if available, accuracy and failure cases. Keep or remove the optional dependency based on evidence. Preserve explicit user model choices and use an approved fallback only when actually needed.

This workflow already supplies metadata-only resume/upgrade selection, targeted inventory, a read-only KB adapter, scoped immutable policy snapshots and compact project handoffs. Start with these rather than a new context server or prompt-compression layer. Actual model prompt caching is runtime-controlled and cannot be guaranteed by a launcher.
